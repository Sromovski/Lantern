# Lantern — Automated Educational Social Content Engine

> Working codename for the *system*. The public pages get their own real names
> (§3). Nothing in the code should depend on either.

## 1. What this is

A content engine that researches, assembles, and automatically publishes short
educational posts to social platforms — one or two a day, per topic area,
forever, with no daily human effort.

The original idea: a page that posts a quote from a famous author (Dickens,
Keats, Shakespeare) with a short, genuinely interesting write-up — who the
author was, what was happening when they wrote it, what the line actually
means — paired with a portrait or a meaningful image.

The generalization: that same shape works for anything worth knowing. Science
facts for kids. How electricity works. Why leaves change color. A math idea
explained in sixty seconds. So the system is **not** a quote bot. It is a
pipeline with a swappable content *vertical* on the front and a set of
platform adapters on the back.

**The point:** kids scrolling their phones hit something that teaches them
instead of something that rots them. That is the product goal, and it is the
tiebreaker for every design decision below. When "more engagement" and "more
actually learned" conflict, pick learned.

## 2. Non-negotiables

These are the rules that make this project worth doing instead of being one
more slop farm.

1. **Never publish an unverified quote.** Misattributed quotes are the single
   most common failure of quote pages, and they are embarrassing forever.
   A quote ships only if it has been located in a primary or near-primary
   source with a citation stored in the database. See §8.
2. **No invented facts.** Every claim in a post's body traces to a stored
   source record. If the enrichment model produces a claim the sources do not
   support, the post fails the gate and does not queue.
3. **Images must be legally clear.** Public domain, CC0, or generated by us.
   The license and source URL are stored per image. No "found it on Google."
4. **Kid-safe by construction for kid verticals.** Reading level target,
   banned-topic list, and a human-reviewable first run. See §9.
5. **Nothing publishes that a human has never seen the *format* of.** Automate
   the labor, not the judgment. The first ~20 posts per channel get eyeballed
   before auto-publish is switched on — and that gate is per *channel*, not per
   vertical, because a format that reads well on Facebook can read badly as a
   Short.
6. **Fail closed.** If any pipeline stage is uncertain, the post goes to
   `needs_review`, not to the platform.
7. **One verified item, many renditions.** Verification happens once, at the
   item level. Formatting happens many times, at the platform level. Never let
   a platform adapter invent content — it only selects and formats what the
   verification gates already approved.

## 3. Scope, audiences, and channels

The routing principle: **go where the audience is, not where it is convenient
to post.** US teen platform usage is YouTube 90%, TikTok 63%, Instagram 61%,
Snapchat 55%, Facebook 32% (Pew, 2025). A page aimed at kids that lives only on
Facebook reaches almost nobody it is for.

So verticals and channels are separate concepts, and a vertical fans out to
whichever channels fit its audience:

| Vertical | Slug | Audience | Primary channels | Later |
|---|---|---|---|---|
| Literature & quotes | `literature` | Adults ~35+, readers | Facebook, Pinterest | Instagram |
| Science for curious minds | `science-curious` | Kids ~8–13 + parents | YouTube Shorts | Instagram, TikTok |

Facebook is genuinely right for literature — quote cards with a thoughtful
write-up are native Facebook content and that audience still shares heavily.
Facebook is genuinely wrong for the kids vertical, so it is not a launch channel
there.

Future verticals to keep in mind while designing (do not build yet): math,
history, art, nature/wildlife, "how things work," vocabulary.

### Branding

Two distinct brands with a shared visual system — **not** "Lantern Literature"
and "Lantern Science." Nobody follows a network; they follow a page about the
thing they like. Tie them together with a consistent design language and a small
shared wordmark, plus cross-links from the archive site (§13).

Literature page candidates:

- **The Commonplace Book** — recommended. A commonplace book is historically
  exactly this: a personal notebook where readers copied passages and
  observations. Distinctive, true, and it gives the About section a real story.
- **Chapter & Verse** — the idiom means "in precise detail, with the citation,"
  which is the verification premise.
- **The Dog-Eared Page**, **Marginalia**, **Footnote**.

Science page candidates:

- **Look Closer** — recommended. Short, handle-friendly, and it is literally the
  instruction every post in that vertical ends with.
- **Small Wonders**, **Curious by Nature**, **The Wonder Lab**.

**Keep "Kids" out of the public name.** On YouTube, content designated "made for
kids" loses comments, notifications, and end screens, which badly damages
growth. Aim for family-friendly-but-not-made-for-kids, and a name that screams
children's content pushes you into that bucket in both viewers' minds and your
own content decisions. The vertical slug (`science-curious`) is internal; the
audience config still targets grade-5 reading level.

Before committing to either name, check the handle on Facebook, Instagram,
YouTube, TikTok, Pinterest **and** the .com at the same time. A name free on
four and taken on the fifth is not free.

## 4. Stack & conventions

- **Node.js + TypeScript**, ESM. Strict mode on.
- **SQLite** via `better-sqlite3`. Single file at `data/lantern.db`.
  Synchronous API, no connection pool nonsense, trivially backed up by copying
  the file. Migrate to Postgres only if this ever becomes multi-user.
- **Migrations:** plain numbered `.sql` files in `migrations/`, applied by a
  tiny runner. No ORM. Write the SQL.
- **Anthropic SDK** (`@anthropic-ai/sdk`) for enrichment and fact-checking.
- **Sharp** for image renditions.
- **Remotion** for video renditions (phase 8, not before). Already proven in the
  brain-teaser reel pipeline — reuse that setup rather than starting over.
- **TTS** for video narration — provider TBD; keep it behind a one-method
  interface so it can be swapped.
- **node-cron** inside a long-lived process, or system cron calling the CLI.
  Prefer system cron — a crashed daemon silently stops posting; a cron job
  leaves a log.
  The CLI locates the project root from its own install location, not the
  working directory (override with `LANTERN_ROOT`); `.env` is read from that
  root, with shell environment variables taking precedence — so a Windows
  Task Scheduler entry needs no "Start in" directory. `lantern doctor` exits
  1 on any failed check and 0 otherwise.
- **Config:** `.env` for secrets (never committed), `config/verticals/*.yaml`
  for vertical definitions, `config/channels/*.yaml` for destinations.
- **Logging:** structured JSON lines to `logs/`, plus a human-readable run
  summary. Every publish writes an audit row.
- Tests with `vitest`. The verification logic (§8) is the part that most needs
  tests; the API wrappers need integration tests against each platform's
  sandbox/test tooling, not unit tests with mocks that lie.

## 5. The content model

This is the most important structural decision in the project, so it gets its
own section.

A verified **item** (a quote, a fact) is the unit of truth. It is verified once.
From it we derive:

- a **post** — the editorial write-up, platform-neutral: hook, body, closer;
- one or more **renditions** — format-specific media artifacts (a 1:1 image, a
  2:3 pin, a 9:16 video);
- one or more **captions** — platform-specific text (a Facebook paragraph, a
  Pinterest keyword description, a YouTube title + description are genuinely
  different objects, not the same string truncated);
- one or more **publications** — a (rendition, caption) pair sent to a channel
  at a scheduled time.

```
item ──► post ──┬──► renditions ──┐
                │                 ├──► publications ──► channel
                └──► captions ────┘
```

Resist the temptation to collapse this into "a post has an image and a caption."
That model is fine until the second platform, and then it is a rewrite.

## 6. Data model

SQLite. Keep it boring and explicit.

```sql
-- A content vertical (literature, science-curious, ...)
CREATE TABLE verticals (
  id            INTEGER PRIMARY KEY,
  slug          TEXT UNIQUE NOT NULL,
  name          TEXT NOT NULL,
  config_path   TEXT NOT NULL,
  active        INTEGER NOT NULL DEFAULT 1
);

-- A configured destination: one platform account for one vertical.
CREATE TABLE channels (
  id             INTEGER PRIMARY KEY,
  vertical_id    INTEGER NOT NULL REFERENCES verticals(id),
  platform       TEXT NOT NULL,      -- 'facebook'|'pinterest'|'youtube'|'instagram'|'tiktok'
  handle         TEXT,               -- public @name, for logs and the review UI
  account_ref    TEXT NOT NULL,      -- env var NAME holding the page/board/channel id
  config_path    TEXT NOT NULL,
  auto_publish   INTEGER NOT NULL DEFAULT 0,  -- 0 = queue to needs_review first
  enabled        INTEGER NOT NULL DEFAULT 1,
  UNIQUE(vertical_id, platform, account_ref)
);

-- A subject: an author, a scientific concept, a phenomenon.
CREATE TABLE subjects (
  id            INTEGER PRIMARY KEY,
  vertical_id   INTEGER NOT NULL REFERENCES verticals(id),
  kind          TEXT NOT NULL,          -- 'author' | 'concept' | 'organism' | ...
  name          TEXT NOT NULL,
  slug          TEXT NOT NULL,
  wikidata_id   TEXT,                   -- Q-number, the join key to everything
  summary       TEXT,                   -- short factual bio/definition
  meta_json     TEXT,                   -- dates, nationality, field, etc.
  created_at    TEXT NOT NULL,
  UNIQUE(vertical_id, slug)
);

-- The unit of truth. Verified once, reused across every platform.
CREATE TABLE items (
  id            INTEGER PRIMARY KEY,
  vertical_id   INTEGER NOT NULL REFERENCES verticals(id),
  subject_id    INTEGER REFERENCES subjects(id),
  kind          TEXT NOT NULL,          -- 'quote' | 'fact' | 'explainer'
  body          TEXT NOT NULL,          -- the quote text, or the core fact
  body_hash     TEXT NOT NULL,          -- normalized hash for dedupe
  work_title    TEXT,                   -- source work, for quotes
  work_year     INTEGER,
  status        TEXT NOT NULL,          -- 'raw'|'verified'|'rejected'
  reject_reason TEXT,
  created_at    TEXT NOT NULL,
  UNIQUE(vertical_id, body_hash)
);

-- Evidence. Every verified item has >= 1. This table is what keeps us honest.
CREATE TABLE sources (
  id            INTEGER PRIMARY KEY,
  item_id       INTEGER NOT NULL REFERENCES items(id),
  tier          INTEGER NOT NULL,       -- 1 = primary text, 2 = scholarly, 3 = reference
  url           TEXT,
  citation      TEXT NOT NULL,          -- human-readable
  excerpt       TEXT,                   -- the matched passage, if applicable
  retrieved_at  TEXT NOT NULL
);

-- Source imagery, before composition.
CREATE TABLE images (
  id            INTEGER PRIMARY KEY,
  subject_id    INTEGER REFERENCES subjects(id),
  item_id       INTEGER REFERENCES items(id),
  origin        TEXT NOT NULL,          -- 'wikimedia'|'loc'|'met'|'nypl'|'openverse'|'generated'
  source_url    TEXT,
  license       TEXT NOT NULL,          -- 'public-domain'|'cc0'|'cc-by'|'generated'
  attribution   TEXT,
  local_path    TEXT NOT NULL,
  width         INTEGER, height INTEGER,
  created_at    TEXT NOT NULL
);

-- The editorial write-up. Platform-neutral prose.
CREATE TABLE posts (
  id            INTEGER PRIMARY KEY,
  item_id       INTEGER NOT NULL REFERENCES items(id),
  vertical_id   INTEGER NOT NULL REFERENCES verticals(id),
  image_id      INTEGER REFERENCES images(id),  -- chosen source image
  hook          TEXT NOT NULL,
  body          TEXT NOT NULL,
  closer        TEXT,
  alt_text      TEXT NOT NULL,
  status        TEXT NOT NULL,          -- 'draft'|'needs_review'|'approved'|'rejected'
  reject_reason TEXT,
  created_at    TEXT NOT NULL,
  UNIQUE(item_id)
);

-- Format-specific media artifacts derived from a post.
CREATE TABLE renditions (
  id            INTEGER PRIMARY KEY,
  post_id       INTEGER NOT NULL REFERENCES posts(id),
  format        TEXT NOT NULL,          -- 'square'|'portrait'|'pin'|'short'|'landscape'
  media_type    TEXT NOT NULL,          -- 'image'|'video'
  aspect        TEXT NOT NULL,          -- '1:1'|'4:5'|'2:3'|'9:16'|'16:9'
  width         INTEGER NOT NULL,
  height        INTEGER NOT NULL,
  duration_ms   INTEGER,                -- video only
  local_path    TEXT NOT NULL,
  public_url    TEXT,                   -- required by Instagram and TikTok
  bytes         INTEGER,
  status        TEXT NOT NULL,          -- 'pending'|'ready'|'failed'
  error         TEXT,
  created_at    TEXT NOT NULL,
  UNIQUE(post_id, format)
);

-- Platform-specific text derived from a post.
CREATE TABLE captions (
  id            INTEGER PRIMARY KEY,
  post_id       INTEGER NOT NULL REFERENCES posts(id),
  platform      TEXT NOT NULL,
  title         TEXT,                   -- YouTube title, Pinterest pin title
  text          TEXT NOT NULL,          -- the body of the caption/description
  hashtags      TEXT,                   -- space-separated, platform-appropriate
  link          TEXT,                   -- Pinterest destination, archive permalink
  char_count    INTEGER NOT NULL,
  created_at    TEXT NOT NULL,
  UNIQUE(post_id, platform)
);

-- One scheduled or completed delivery: a rendition + caption to a channel.
CREATE TABLE publications (
  id              INTEGER PRIMARY KEY,
  post_id         INTEGER NOT NULL REFERENCES posts(id),
  channel_id      INTEGER NOT NULL REFERENCES channels(id),
  rendition_id    INTEGER NOT NULL REFERENCES renditions(id),
  caption_id      INTEGER NOT NULL REFERENCES captions(id),
  status          TEXT NOT NULL,        -- 'scheduled'|'publishing'|'published'|'failed'|'skipped'
  scheduled_for   TEXT,
  published_at    TEXT,
  remote_id       TEXT,                 -- platform-returned post id
  permalink       TEXT,
  idempotency_key TEXT NOT NULL,        -- hash(post_id, channel_id); guards double-posting
  attempt         INTEGER NOT NULL DEFAULT 0,
  error           TEXT,
  UNIQUE(post_id, channel_id),
  UNIQUE(idempotency_key)
);

-- Pipeline observability.
CREATE TABLE run_log (
  id            INTEGER PRIMARY KEY,
  vertical_id   INTEGER,
  channel_id    INTEGER,
  stage         TEXT NOT NULL,
  ok            INTEGER NOT NULL,
  detail_json   TEXT,
  created_at    TEXT NOT NULL
);
```

Indexes: `items(status, vertical_id)`, `items(body_hash)`,
`posts(status, vertical_id)`, `renditions(post_id, status)`,
`publications(status, scheduled_for)`, `publications(channel_id, published_at)`,
`run_log(stage, created_at)` (for `doctor` health checks that query by stage and time).

All TEXT timestamp columns hold UTC ISO-8601 strings with a `Z` suffix (as
produced by `Date.prototype.toISOString()`), so they compare correctly as
strings; local times such as channel cadence `times` are converted to UTC
before they are stored.

The `UNIQUE(post_id, channel_id)` on `publications` is the single most important
constraint in the schema: it makes double-posting the same content to the same
page structurally impossible, not merely unlikely.

## 7. Pipeline

Each stage is a separate CLI subcommand, idempotent, and safe to re-run. The
scheduler just calls them in order. Nothing is a long-lived in-memory pipeline;
state lives in SQLite between every stage.

```
harvest → verify → enrich → media → compose → render → caption → queue → publish
                                      (images)  (video)
```

**`lantern harvest --vertical literature --limit 25`**
Pull raw candidate items from the vertical's configured sources. Writes `items`
rows with `status='raw'`. Dedupes on `body_hash` (lowercased, punctuation and
whitespace normalized, smart quotes folded) so the same line never enters twice.

**`lantern verify --vertical literature`**
Runs the attribution gates (§8). Promotes to `verified` with `sources` rows, or
marks `rejected` with a reason. Rejections are kept, not deleted — they are the
dedupe memory that stops us re-harvesting the same bad quote monthly.

**`lantern enrich --vertical literature --limit 5`**
Claude call. Given the item, its subject, and its stored sources, write the
platform-neutral post: hook, body, closer. Structured output. The prompt is in
the vertical config so each vertical has its own voice. A second Claude call
(different prompt, sources-only context) checks the draft for claims not
supported by the provided sources; unsupported claims send the post to
`needs_review` rather than silently dropping the sentence.

**`lantern media --vertical literature`**
Resolve a source image (§10). Public domain first, AI generation as fallback.
Stores license + attribution on the `images` row and links it to the post.
Never overwrites an image on an already-approved post.

**`lantern compose --post 123 --formats square,pin`**
Render image renditions with Sharp from the post's source image + text. One
`renditions` row per format. Safe to re-run; regenerating a format replaces that
row only.

**`lantern render --post 123 --format short`**
Video renditions via Remotion + TTS. Separate from `compose` because it is slow,
expensive, and fails differently — a failed video render must not invalidate a
perfectly good square image. Phase 8.

**`lantern caption --post 123 --platforms facebook,pinterest`**
Generate per-platform text from the post. Enforces each platform's limits and
conventions (§11). Writes `captions` rows. This is a formatting step over
already-verified content — it may not introduce new claims, and the fact-check
gate re-runs against any caption that isn't a pure truncation.

**`lantern queue --channel literature-facebook`**
Select posts whose required renditions and captions are `ready`, and create
`publications` rows with `scheduled_for` set per the channel's cadence and the
spacing rules in §12.

**`lantern publish`**
Take every publication with `scheduled_for <= now` and `status='scheduled'`,
hand it to the right adapter, record the result. Retries with backoff; three
failures marks it `failed` and alerts.

**`lantern review`**
Small local web UI on `localhost:4321` showing the `needs_review` queue: every
rendition side by side, each caption, sources with links, approve/reject/edit.
This is the human-judgment surface and is worth building well — it is where
quality actually gets enforced in the first weeks. Show the renditions at true
phone scale; a caption that reads fine on a laptop can be illegible as a
thumbnail.

**`lantern doctor`**
Health check per channel: token validity and days-to-expiry, quota headroom, DB
integrity, queue depth, last successful publish, disk usage. Run it daily; it is
how you find out a token expired *before* a page goes quiet for a week.

Every stage writes a `run_log` row on entry and exit — stage, vertical, channel,
ok/failed, and a JSON detail blob. That table is what `doctor` reads and what
makes "why did nothing post on Tuesday" answerable after the fact.

## 8. Verification — the part that matters

**Quotes (literature vertical).** A quote is `verified` only if it passes one of:

- **Tier 1:** The exact string (normalized) is located in a public-domain
  full text — Project Gutenberg via the Gutendex API, Standard Ebooks, or
  Wikisource. Store the work, the location, and the matched excerpt. This is the
  strongest evidence and the preferred path. Prefer harvesting *from* the texts
  themselves rather than from quote sites; a passage pulled out of Bleak House
  is verified by construction.
- **Tier 2:** Attested in a scholarly or editorial source with a citation
  (Oxford/Yale editions, a university page, the author's collected letters).
- **Tier 3 alone is never enough.** Wikiquote is useful as a *lead generator* and
  especially useful for its "Misattributed" and "Disputed" sections — check
  those explicitly and hard-reject anything appearing there. But a Wikiquote
  entry is not, by itself, verification.

Quote aggregator sites (BrainyQuote, Goodreads quotes, AZQuotes and friends) are
**banned as sources**. They are the primary vector for misattribution and they
launder each other's errors. They may not appear in `sources` at all. This ban,
and the rule that every verified item needs at least one tier 1 or tier 2
source, are enforced by SQLite triggers in `migrations/002_source_guards.sql`.

Additional hard rejects: quotes attributed to an author who died before the
phrasing existed; any quote whose earliest traceable appearance is post-1990
internet; "Shakespeare" quotes not found in the First Folio or the accepted
canon; anything whose sources conflict on the attribution.

**Facts (science vertical).** Every fact needs at least one Tier 1 or Tier 2
source: a `.gov`/`.edu` page, NASA, NOAA, USGS, Smithsonian, a museum, a
textbook, or a peer-reviewed paper. Numbers in the body must match the number in
the source exactly — this is a programmatic check, not a vibe check: extract
numerals from the draft, confirm each appears in a stored source excerpt.

Store the retrieval date. Facts age; a "newest planet discovered" post rots.
Prefer durable facts over current-record facts.

**Verification is item-level and happens once.** A rendition or caption never
re-opens it. This is what makes fan-out to five platforms safe.

## 9. Voice & safety per vertical

Defined in `config/verticals/*.yaml`:

```yaml
slug: science-curious
name: Look Closer
kid_safe: true
audience:
  reading_level: grade-5      # enforced; check with a readability score
  age_range: [8, 13]
voice: |
  Curious, plain, never condescending. Short sentences. One idea per post.
  Explain the mechanism, not just the name of the thing. End with a question
  that makes a kid want to go look at something in the real world.
  Never: "Did you know?!", exclamation stacks, emoji walls, clickbait.
post_shape:
  hook: 1 sentence
  body: 3-5 short paragraphs
  closer: 1 question
banned_topics:
  - graphic injury or death
  - weapons and explosives beyond textbook chemistry
  - anything requiring a safety warning to try at home
  - politics, religion, current events
image:
  style: bright, clear, single-subject, no text in the generated image
  generated_disclosure: true
```

Channel configs live separately and hold cadence, formats, and limits:

```yaml
# config/channels/science-youtube.yaml
vertical: science-curious
platform: youtube
account_ref: YT_CHANNEL_ID_LOOK_CLOSER
formats: [short]
cadence:
  posts_per_day: 1
  times: ["16:30"]            # after school, local time
made_for_kids: false          # family-friendly, not COPPA-designated — see §3
caption:
  title_max: 100
  text_max: 5000
```

`auto_publish` lives only in the `channels` DB column (§6), never in channel YAML —
that keeps the per-channel human review gate from being bypassable by a config edit.

**Always disclose AI-generated images** in the caption ("Illustration:
AI-generated"). Cheap to do, and the first time someone catches an undisclosed
generated portrait of Dickens the page's credibility is gone.

**Never AI-generate a portrait of a real person.** For authors, public domain
portraits exist for essentially everyone in scope — if none is found, use the
book's title page, a manuscript page, or a period image of the setting instead.
Generation is for concepts and phenomena, not faces.

## 10. Image sourcing

Public domain first, in this order:

1. **Wikimedia Commons** — MediaWiki API. Resolve the subject's Wikidata
   Q-number, read the `P18` (image) property, then pull the file and its license
   metadata. This covers nearly every historical author.
2. **Library of Congress** — `loc.gov` JSON API. Strong for American subjects,
   photographs, and historical prints.
3. **Met Museum Open Access** — public API, no key, `isPublicDomain` flag.
   Excellent for art and objects.
4. **NYPL Digital Collections** — API key required. Good for manuscripts and
   period material.
5. **Openverse** — aggregator; useful as a sweep, but re-check the license on
   the original source before use.

Always confirm the license programmatically from the API response. Never infer
"it's old so it's fine" — re-photographs and restorations can carry their own
claims. Store `license` and `attribution`, and render attribution in the caption
when the license asks for it.

**Resolution matters more now.** A source image has to survive being cropped to
both 1:1 and 9:16. Reject sources below ~1500px on the short edge, and store
enough of the original that a re-crop never needs a re-download.

**AI fallback** fires only when PD search returns nothing usable, and only for
non-portrait subjects. Prompt built from the item's body and the vertical's
image style. Generated images are marked `license='generated'` and disclosed.

**Composition** (Sharp): one template per (vertical, format) so the feed reads as
one brand — same margin system, same two typefaces, same wordmark placement,
adapted per aspect rather than naively letterboxed. Text must stay legible at
phone thumbnail size: large type, high contrast, a scrim over busy photographs.
Build the templates once, check them on an actual phone, then stop fiddling.

## 11. Platforms

Every adapter implements the same interface and declares what it can take:

```ts
interface Publisher {
  readonly platform: Platform;
  readonly requiredFormat: RenditionFormat;   // which rendition it needs
  readonly needsPublicUrl: boolean;           // IG and TikTok do
  publish(input: PublishInput): Promise<PublishResult>;
  healthCheck(): Promise<HealthStatus>;
}
```

Rendition matrix:

| Format | Aspect | Pixels | Type | Used by |
|---|---|---|---|---|
| `square` | 1:1 | 1200×1200 | image | Facebook |
| `portrait` | 4:5 | 1080×1350 | image | Instagram feed |
| `pin` | 2:3 | 1000×1500 | image | Pinterest |
| `short` | 9:16 | 1080×1920 | video | YouTube Shorts, Reels, TikTok |
| `landscape` | 16:9 | 1200×630 | image | archive site, link previews |

### Facebook (phase 4)

`POST /{page-id}/photos` with a Page access token: `url` or `source`, `caption`,
`published=true`. Permissions: `pages_manage_posts`, `pages_read_engagement`,
plus `pages_show_list` to enumerate Pages during setup.

Token flow, which is the part that bites everyone:

1. User access token from Facebook Login (you, as the Page admin).
2. Exchange for a **long-lived user token** (~60 days).
3. Call `GET /me/accounts` with that to get a **Page access token** — Page
   tokens derived from a long-lived user token do not expire, which is what
   makes unattended posting possible.
4. Store it encrypted, never in the repo. `lantern doctor` checks it via
   `GET /debug_token`.

App Review is required before the app can act on Pages beyond a dev capacity.
Budget real calendar time. Screencast a working demo of the posting flow; that
is what gets approvals through.

> **Confirm at build time:** the current Graph API version string and the exact
> permission set Meta requires this quarter. Both change. Read
> `developers.facebook.com/docs/pages-api` before writing the adapter rather
> than trusting this file.

### Pinterest (phase 6)

The cheapest second channel: image-only, reuses the whole pipeline, needs one
new rendition format and one adapter. Pinterest API v5, `POST /pins` with a
board id, image, title, description, and destination link.

Pinterest is search-driven rather than feed-driven, so pins keep earning
impressions for years — which suits evergreen content far better than a feed
does. Two consequences for the adapter: captions should be written for **search**
(plain keywords, no hashtag spam), and every pin should carry a `link` back to
the archive site (§13), which is where Pinterest's real value shows up.

### YouTube Shorts (phase 8)

The best fit for the kids vertical — 90% teen reach, and the only platform where
content genuinely accrues: an evergreen "how does electricity work" Short keeps
being found by search for years.

`videos.insert` via the YouTube Data API. Quota math is comfortable: the default
allowance is 10,000 units/day and `videos.insert` costs ~1,600, so ~6 uploads a
day against a target of 1–2. Uploads under 60s in 9:16 are treated as Shorts
automatically; no separate endpoint.

Set `madeForKids: false` deliberately for a family-friendly-but-not-designated
channel (§3) — but read YouTube's current COPPA guidance and make that call
consciously, because getting it wrong in either direction has consequences.

### Instagram (phase 9)

Nearly free once Facebook works — same Meta app, same review. Two-step: create a
media container (`POST /{ig-user-id}/media`), then `POST /{ig-user-id}/media_publish`.
Requires an IG Business/Creator account linked to the Page, and there is a daily
publishing limit (25 posts/24h at last check).

**Instagram will not accept a local upload** — it needs a publicly reachable
image or video URL. This is why `renditions.public_url` exists, and it is a
hosting dependency: the archive site or a small static bucket has to serve
rendition files before this phase can ship.

### TikTok (deferred — export only)

Best discovery engine available, worst API access. The Content Posting API
restricts unaudited clients to 5 users per 24h, private accounts only, and
`SELF_ONLY` visibility — you would have to flip each post public by hand.

The harder problem is the audit criteria: TikTok requires the app to "facilitate
authentic creators to post original content" and says apps "should not be
limited to internal use but designed for a wide audience." A personal automation
tool posting to your own accounts is close to the definition of what they
decline. There is also a ~15 posts/day/creator cap across all API clients.

**Plan:** build `tiktok.ts` as an *export* adapter — it writes the 9:16 rendition
and caption to a dated folder for manual upload — and revisit direct posting only
if the account grows into something TikTok would plausibly audit.

### Not doing

**Reddit.** Content fits beautifully, automated posting gets you banned quickly,
and those communities are good at spotting it. If it ever happens, it happens by
hand.

### Rate limiting & retries

Respect each platform's headers. Exponential backoff on 5xx and rate limits.
Never retry a 4xx that is not a rate limit — fix it instead. Every attempt
increments `publications.attempt`; the `UNIQUE(post_id, channel_id)` constraint
plus `idempotency_key` make a duplicate post structurally impossible even if a
retry races.

## 12. Scheduling

**Cadence.** One or two posts a day per *channel*. More is not better; it
exhausts your verified backlog and, on feed platforms, gets throttled. Keep a
**minimum 30-day buffer of approved posts per channel** — the whole value
proposition is that it runs while you do not think about it, and that only works
if the queue is deep.

**Spacing rules** enforced at `queue` time, scoped per channel:

- No two posts from the same subject within 30 days.
- No two posts from the same source work within 14 days.
- Vary item `kind` across consecutive days where the vertical has more than one.
- Add ±15 minutes of jitter so it does not look robotic.

**Cross-channel timing.** The same post may legitimately go to Facebook and
Pinterest, but not within the same hour — stagger by at least a day so the
overlapping slice of an audience does not see the same thing twice in a morning.
Different verticals have no such constraint.

## 13. The archive site

Promoted out of "open questions" because three other things now depend on it:

- Instagram and TikTok need publicly reachable rendition URLs.
- Pinterest pins want a destination link, and that link is most of Pinterest's
  value.
- It is the only channel you own. Every platform above can change its mind about
  you; the archive cannot.

Minimum viable version: a static site generated from the database, one page per
post with the write-up, the image, and the sources visible. That last part is a
differentiator — a quote page that *shows its citations* is unusual, and it is
the natural place to point anyone who asks "is that real?"

Good SEO target as a side effect, and the natural home for an email list later.

## 14. Build phases

**Phase 1 — spine (no APIs).** Repo, TypeScript config, SQLite schema and
migrations, CLI skeleton, config loader, logging. *Done when:* migrations run
clean and `lantern doctor` reports a healthy empty system.

**Phase 2 — literature content, end to end, no publishing.** Gutendex harvester,
verification gates with real tests, Claude enrichment, Wikimedia image lookup,
Sharp composition for `square` + `pin`, Facebook and Pinterest captions.
*Done when:* 20 finished literature posts exist on disk in both formats that you
would be happy to publish.

**Phase 3 — review UI.** The local queue viewer, renditions shown at phone
scale. *Done when:* you can approve or reject a post in two clicks and see its
sources.

**Phase 4 — Facebook publishing.** Meta app, tokens, adapter, manual single
publish, then scheduled. Start with the Page unpublished or tiny.
*Done when:* a post appears on the Page without you touching Meta's UI.

**Phase 5 — automation.** Cron entries, buffer monitoring, alerting when a
channel queue drops below 30 days or a publish fails. *Done when:* it runs a
full week untouched.

**Phase 6 — Pinterest.** Second platform, image-only, no new pipeline stages.
*Done when:* the same approved post reaches two platforms on its own schedule.
This is the phase that proves the fan-out model; if it is painful, fix §5–6
before going further.

**Phase 7 — science vertical.** Build `science-curious` by writing a config and
one new harvester. If that takes more than a day, the abstraction was wrong —
fix it rather than special-casing.

**Phase 8 — video + YouTube Shorts.** The archive site (§13) ships here too,
because rendition hosting becomes a dependency. Remotion + TTS, `short` format,
`videos.insert`. Biggest single phase; do not start it before phases 1–7 are
boring.

**Phase 9 — Instagram.** Cheap once Meta review and public URLs both exist.

**Phase 10 — growth.** TikTok by hand, email list, more verticals. Only after
the existing channels have run clean for a month.

## 15. Working agreements for Claude Code

- Build one pipeline stage at a time, with its tests, before starting the next.
  A half-built pipeline that runs end to end beats a fully-built harvester with
  nothing downstream.
- **Never let a platform adapter generate content.** Adapters select and format;
  they do not write. If an adapter needs text that does not exist, the fix is a
  `caption` stage change, not an inline Claude call in `publish/`.
- Prefer real integration over mocks for the source APIs — cache the responses
  in `data/cache/` so tests are fast and offline but exercise real shapes.
- Never commit `.env`, `data/lantern.db`, or anything under `data/media/`.
- When a source or platform API shape is unknown, fetch one real response and
  look at it before writing the parser.
- Verification code gets tests first. Everything else can be tested after.
- Keep the Claude prompts in version-controlled files, not string literals
  buried in TypeScript. They are content, and they will be tuned often.
- If a design decision here turns out wrong once real data is flowing, change
  this file in the same commit as the code. A stale CLAUDE.md is worse than none.
